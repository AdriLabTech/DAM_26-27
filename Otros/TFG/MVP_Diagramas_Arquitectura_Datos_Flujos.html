Traducción del documento del MVP a diagramas que se pueden implementar directamente: arquitectura, entidades y relaciones, estados, secuencias y reglas de control.

Supuestos que he tomado donde el documento no los fija: autorización por roles y permisos en tablas (no solo un enum), carrito persistido en servidor, precios copiados al crear el pedido (snapshot), WebSocket con STOMP sobre Spring, y un servicio auxiliar updater para aplicar actualizaciones. Todos son decisiones fáciles de revertir si prefieres otra opción.

Comunicación entre componentes

Regla del documento: REST para operaciones normales, WebSocket solo para eventos en tiempo real. Internamente, los módulos del backend no se llaman entre sí para efectos secundarios (puntos, notificaciones, auditoría): publican eventos de dominio y los demás reaccionan.

Decisiones del modelo

  • Roles y permisos en tablas. Cumple tu requisito de no repartir if (user.isAdmin()) por el código: los controladores usan @PreAuthorize("hasAuthority('PRODUCT_WRITE')") y los permisos se cargan desde role_permission.
  • Un único registro de configuración. installation_settings tiene una sola fila (id = 1, con CHECK (id = 1)): refuerza la idea de instalación independiente, sin tenant_id en ninguna tabla.
  • Feature flags con clave de texto. Añadir un módulo futuro (pago, delivery) es insertar una fila y una migración, no cambiar el esquema.
  • Snapshots en el pedido. Nombre, precio unitario, subtotal, descuento y total se guardan en el pedido para que el historial sea inmutable.
  • Historial de estados. order_status_history permite el detalle de pedido, la auditoría y calcular tiempos de preparación sin tablas extra.
  • Baja lógica. Productos y categorías usan active en vez de borrarse si tienen pedidos asociados (clave foránea). El «eliminar» del CRUD hace borrado físico solo si no hay referencias.
  • Índices recomendados: customer_order(status, created_at) para el kanban, customer_order(customer_id, created_at DESC) para el historial, notification(user_id, read_at), reservation(reserved_at, status), audit_log(entity_type, entity_id).
  • Auditoría básica en todas las tablas: created_at y updated_at (omitidos en algunos recuadros por espacio).

Máquinas de estado

Pedido

Quién puede ejecutar cada transición. El backend valida el estado de origen: un COMPLETED nunca vuelve atrás.

stateDiagram-v2
  [*] --> PENDING : cliente crea el pedido
  PENDING --> ACCEPTED : empleado acepta
  ACCEPTED --> PREPARING : empleado inicia preparación
  PREPARING --> READY : empleado marca listo
  READY --> COMPLETED : empleado entrega
  PENDING --> CANCELLED : cliente o empleado
  ACCEPTED --> CANCELLED : empleado
  PREPARING --> CANCELLED : manager o admin
  COMPLETED --> [*]
  CANCELLED --> [*]

El cliente solo cancela mientras el pedido está en PENDING. Cancelar tras PREPARING exige MANAGER o ADMIN (decisión de negocio ajustable).

Flujo · Registro, verificación y login

sequenceDiagram
  autonumber
  actor U as Cliente
  participant W as Web cliente
  participant API as Backend REST
  participant DB as PostgreSQL
  participant M as SMTP

  U->>W: Rellena el formulario de registro
  W->>API: POST /api/auth/register
  API->>API: Valida DTO y hash de contraseña
  API->>DB: INSERT user_account y customer_profile
  API->>DB: INSERT verification_token (hash)
  API->>M: Envía enlace de verificación
  API-->>W: 201 Created
  U->>W: Abre el enlace del correo
  W->>API: POST /api/auth/verify-email
  API->>DB: Marca email_verified y consume el token
  API-->>W: 200 OK

  U->>W: Introduce email y contraseña
  W->>API: POST /api/auth/login
  API->>DB: Busca usuario y compara hash
  alt Credenciales válidas y cuenta ACTIVE
    API->>DB: INSERT refresh_token (hash)
    API-->>W: access token corto y refresh token
  else Inválidas o cuenta desactivada
    API-->>W: 401 con código de error común
  end
  Note over W,API: El access token viaja en la cabecera Authorization
El refresh token se rota en cada renovación

Flujo · Crear un pedido y verlo en el kanban

Es el flujo que justifica toda la arquitectura: un POST del cliente aparece en la pantalla del empleado sin refrescar.

sequenceDiagram
  autonumber
  actor C as Cliente
  participant W as Web cliente
  participant API as OrderController
  participant OS as OrderService
  participant CS as CouponService
  participant LS as LoyaltyService
  participant DB as PostgreSQL
  participant BUS as Event bus
  participant WS as Broker WebSocket
  participant E as App de empleados

  C->>W: Pulsa Confirmar pedido
  W->>API: POST /api/orders
  API->>API: JWT válido, permiso ORDER_CREATE, módulo orders activo
  API->>OS: createOrder(customerId, cartId, couponCode, pointsToUse)
  OS->>DB: Lee carrito y productos
  OS->>OS: Verifica disponibilidad y recalcula precios en servidor
  opt Hay cupón y el módulo coupons está activo
    OS->>CS: validate(code, customerId, subtotal)
    CS-->>OS: descuento aplicable
  end
  opt Usa puntos y el módulo loyalty está activo
    OS->>LS: reserve(customerId, points)
    LS-->>OS: descuento por puntos
  end
  OS->>DB: INSERT customer_order, order_item, status_history
  OS->>DB: Registra canje de cupón y vacía el carrito
  OS->>BUS: publish OrderCreated
  Note over OS,DB: Todo lo anterior ocurre en una sola transacción
  DB-->>OS: COMMIT
  OS-->>API: OrderDto
  API-->>W: 201 Created con el pedido
  BUS->>WS: después del commit, evento ORDER_CREATED
  WS-->>E: /topic/staff/orders
  E->>E: Aparece en la columna PENDIENTE sin recargar

El servidor nunca confía en los precios que envía el cliente: los recalcula desde la base de datos.

    BUS->>WS: ORDER_STATUS_CHANGED
    WS-->>K: /topic/staff/orders
    WS-->>C: /user/queue/orders

    BUS->>AU: registra la acción

Cada suscriptor falla de forma independiente: si la notificación falla, el estado del pedido ya está confirmado.

Cierre del MVP

Lo que los diagramas dejan cubierto de principio a fin: un establecimiento instala el sistema y lo configura, crea productos y empleados; un cliente se registra y hace un pedido; el empleado lo gestiona en tiempo real y el cliente recibe cada cambio de estado; el administrador activa o desactiva módulos y la instalación se actualiza conservando sus datos.

Fuera del MVP, como dice el documento: pagos reales, delivery, stock avanzado, app nativa, IA, analítica avanzada, multi-tenant y SaaS centralizado. El modelo ya deja el hueco para ellos (feature flags onlinePayment y delivery en false) sin crear tablas que no se usan.
